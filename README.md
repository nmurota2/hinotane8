# hinotane — 日本株スイングトレードの半自動化システム

毎晩 LINE に「明日の候補銘柄」が届き、**「買う」を押したものだけ**を翌朝の寄り付きに発注する。

```
21:00  📱 LINE に候補が届く（銘柄・根拠・損切り価格・数量・最大損失額）
        ↓  あなたが「買う」か「見送る」を押す
08:50  🤖 承認したものだけ発注
16:10  🔚 損切り・利確・時間切れを自動判定して決済
```

> ### 🛡️ いきなりお金は動きません
> 初期設定は **擬似発注モード（PaperBroker）** です。`.env` の `LIVE_TRADING` を
> 明示的に `true` にしない限り、何をしても実際の注文は出ません。
> まずは擬似発注で成績を貯めてから、実取引に進んでください。

## 1. 必要なもの

| # | 必要なもの | 費用 | 所要 | 何に使うか |
|---|---|---|---|---|
| 1 | [J-Quants](https://jpx-jquants.com) アカウント | 無料〜1,650円/月 | 5分 | 株価・財務データ（JPX公式） |
| 2 | [LINE Developers](https://developers.line.biz) の Messaging API チャネル | 無料 | 15分 | 通知と承認ボタン |
| 3 | VPS（ConoHa / さくらVPS など、Ubuntu）＋ ドメイン | 約700円/月＋年1,000円 | 20分 | 承認ボタンの受け口と24時間実行 |
| 4 | **立花証券 e支店** の口座 | 無料 | 数日〜2週間 | 実発注（Phase 4 で必要） |

### 🚀 まずは 1 と 2 だけでいい

**「毎晩 LINE に候補が届く」だけなら、VPS もドメインも要りません。**
お手元の PC で `hinotane screen` を実行すれば LINE に飛びます（通知の送信に受け口は不要なため）。

3 が要るのは**承認ボタンから発注まで**やる段になってから。4 はさらにその先です。

> **👉 Mac の方は [`docs/04_mac_quickstart.md`](docs/04_mac_quickstart.md) を最初に読んでください。**
> ターミナルの開き方からコピペで進められる手順書です。
>
> **👉 J-Quants / LINE の取得手順は [`docs/03_setup_guide.md`](docs/03_setup_guide.md)。**
> 「プラン選択を忘れると API が動かない」など、つまずきやすい箇所を先回りして書いてあります。

> ### ⚠️ 証券口座について、先に知っておいてほしいこと
> **SBI証券・野村證券・楽天証券には、個人向けの発注APIが存在しません。**
> （楽天は Windows 専用の Excel アドインのみ、SBIネオトレード証券も Excel 専用）
>
> クラウドで 24 時間動かしながら発注まで行える日本株の API は、
> **立花証券 e支店 API**（無料・Linux/Python で完結）が事実上唯一の選択肢です。
>
> 口座開設時は必ず「**e支店**」を選んでください。「ストックハウス」で開設すると
> API が使えないうえ、**一度解約しないと e支店側に口座を作れません。**

> ### ⚠️ J-Quants の無料プランは 12 週間遅延です
> 無料プランでも**バックテストと動作確認は十分できます**が、
> 「明日の候補」を出すには当日データが必要なので、
> 実運用には **Light プラン（月1,650円）以上**が必要です。
> データが古いときは通知に自動で警告が出ます。

## 2. 30分でのセットアップ

### 2-1. 取得する

```bash
git clone <このリポジトリのURL> hinotane
cd hinotane
```

### 2-2. セットアップスクリプトを実行する（推奨・macOS / Linux / VPS）

```bash
bash scripts/setup.sh
```

Python 環境の作成 → パッケージ導入 → `.env` 生成 → API キーの入力 → 動作確認 までを
一度にやります。**API キーは入力中も画面に表示されず、`.env` にだけ保存されます。**
何度実行しても壊れないので、設定を変えたいときは再実行してください。

これが通ったら **2-5 へ進んでください**（2-3 と 2-4 は手動でやる場合の手順です）。

<details>
<summary>手動でやる場合／Windows の場合</summary>

```bash
python3 -m venv .venv
source .venv/bin/activate          # Windows は .venv\Scripts\activate
pip install -e ".[dev]"
cp .env.example .env               # Windows は copy .env.example .env
```
</details>

### 2-3. 設定ファイルを編集する

`.env` をエディタで開いて、次の 3 か所だけ埋めます。

```dotenv
# ① J-Quants のダッシュボードで発行した API キー
JQUANTS_API_KEY=あなたのAPIキー

# ② LINE Developers → Messaging API チャネルから取得
LINE_CHANNEL_ACCESS_TOKEN=あなたのトークン
LINE_CHANNEL_SECRET=あなたのシークレット

# ③ あなたの運用資金（円）。ポジションサイズの計算基準になる
RISK_EQUITY_JPY=1000000
```

> J-Quants が V1（メールアドレス＋パスワード方式）の場合は、`JQUANTS_API_KEY` を空にして
> `JQUANTS_MAIL_ADDRESS` と `JQUANTS_PASSWORD` を埋めてください。どちらでも動きます。

### 2-4. 動作確認

```bash
hinotane doctor
```

設定の健康診断が走ります。**実際に J-Quants API を1回叩いて、鍵が本当に通るかまで確認します。**

```
✅ J-Quants: 接続成功（認証方式: APIキー (V2) / 4,412 銘柄）
```

❌ になる場合、最も多い原因は **J-Quants のダッシュボードでプラン選択が未完了**です
（Free プランでも選択操作が必要）。詳しくは [docs/03_setup_guide.md](docs/03_setup_guide.md) を参照。

### 2-5. 過去データを取り込む（初回のみ・数十分かかります）

```bash
hinotane backfill --years 2
```

2 年ぶんの全銘柄日足を取り込みます。バックテストの土台になります。
時間がかかるので、`--years 1` で始めても構いません。

### 2-6. スクリーニングを試す（LINE には送らない）

```bash
hinotane screen --dry-run
```

こんな出力が出れば成功です。

```
📈 本日の候補 2 銘柄
基準日: 2026-08-07 ／ 運用資金 1,000,000円
モード: 擬似発注

[1] 7203 トヨタ自動車  —  上昇トレンドの押し目
     根拠 : 75日線上の上昇トレンド / 25日線まで押し目(-1.6%) / RSI47 / 陽線で反発
     入り :     3,110 円
     損切 :     3,020 円 (-2.9%)
     利確 :     3,290 円 (+5.8%)  R/R 2.0倍
     数量 :       100 株   必要資金 311,000 円
     最大損失 : 9,000 円
```

### 2-7. LINE の userId を登録する

**LINE Developers コンソール →「チャネル基本設定」タブ → 一番下の「あなたのユーザーID」**
をコピーして設定します。

```dotenv
LINE_ALLOWED_USER_IDS=Uxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
```

**この ID に登録された人だけが承認できます。**未設定だと通知は送られません。

> 見つからないときは、`.env` にトークンとシークレットだけ入れて `hinotane serve` を起動し、
> Bot に話しかけてください。**「あなたの userId はこれです」と返信で教えます**（セットアップモード）。
> この状態では承認操作を一切受け付けないので安全です。

### 2-8. 通知が届くか試す

```bash
hinotane line-test
```

LINE にテストメッセージが届けば設定完了です。

## 3. 毎日の動き

VPS に置くと、以下が自動で回ります（`deploy/crontab` で定義）。

| 時刻 | コマンド | 内容 |
|---|---|---|
| 16:00 | `hinotane fetch` | 引け後の日足を取得 |
| 16:10 | `hinotane mark` | 建玉の損切り・利確・時間切れを判定して決済 |
| 21:00 | `hinotane screen` | スクリーニング → LINE に候補を配信 |
| 08:50 | `hinotane execute` | 承認済みシグナルを発注 |

手で動かすときも同じコマンドです。

## 4. LINE での操作

### 通知カードのボタン
- **買う** … 承認。翌朝の寄り付きに発注されます
- **見送る** … 却下

承認には**有効期限（既定 18 時間）**があります。期限を過ぎた承認は執行されません。
「夜に承認 → 忘れる → 3日後に約定していた」を防ぐためです。

### トークに送れるコマンド（何回送っても無料）

| 送る言葉 | 返ってくるもの |
|---|---|
| `状況` | データの鮮度・保有銘柄数・未承認シグナル数・現在のモード |
| `保有` | 建玉の一覧（数量・取得単価・損切り価格・目標） |
| `成績` | 確定損益のサマリ（取引数・勝率・合計損益） |
| `停止` | 🛑 未承認のシグナルを全部取り消す |

> **課金の話**: LINE の無料プランは月 200 通まで（push のみカウント）。
> 1日1回の配信なら月 20 通程度なので余裕で収まります。
> 上のコマンドへの返信は reply API なので **1 通もカウントされません**。

## 5. 戦略とバックテスト

### 用意されている戦略

| 名前 | 中身 | 損切り | 利確 | 最大保有 |
|---|---|---|---|---|
| `breakout` | 20日高値ブレイク。上昇トレンド中に出来高を伴って直近高値を上抜けた日 | エントリー − 2.0×ATR | リスク幅の 2.5倍 | 20営業日 |
| `pullback` | 上昇トレンドの押し目。75日線の上で25日線まで押し、RSI が中立以下 | エントリー − 1.5×ATR | リスク幅の 2.0倍 | 15営業日 |
| `reversal` | 売られすぎ反発。RSI30以下＋下ヒゲ陽線＋出来高増 | 当日安値の直下 | リスク幅の 1.8倍 | 10営業日 |

使う戦略は `.env` の `SCREENER_STRATEGIES` で切り替えます。

### バックテスト

```bash
hinotane backtest                        # 設定中の全戦略
hinotane backtest --strategies breakout  # 1つだけ
```

### ⭐ 過剰最適化のチェック（これを必ずやってください）

```bash
hinotane walkforward
```

データを前半・後半に分けて、**前半だけで良い成績が出ていないか**を判定します。

```
[イン・サンプル（前半）]     期待値 +0.35 R
[アウト・オブ・サンプル（後半）] 期待値 +0.31 R

=== 判定 ===
✅ 前半・後半で期待値が保たれています。
```

後半で期待値がマイナス、または半分以下に落ちる戦略は **実運用に載せないでください**。
過去に当てはめただけで、先には効きません。

### バックテスト結果の読み方

- **期待値（R）** ここが最重要。1トレードあたり「損切り幅の何倍」取れたか。**プラスでなければ話になりません**
- **勝率** 低くても期待値がプラスなら問題ありません（順張りは勝率40%前後が普通）
- **最大DD** 資産が最大何%減ったか。これに精神的に耐えられるかを自問してください
- **プロフィットファクター** 総利益 ÷ 総損失。1.5以上が目安

> ### ⚠️ バックテスト結果の限界（正直に書きます）
> 1. **生存者バイアス** — DB は「取得時点で上場している銘柄」だけなので、途中で上場廃止になった銘柄が入っていません。**結果は実態よりやや良く出ます**
> 2. **流動性** — 約定コストは一律のスリッページで近似しています。薄い銘柄では実際にはもっと不利になります
> 3. バックテストは戦略同士の**相対比較**として読んでください。絶対値を信じないこと

## 6. 安全装置

コードで強制している制約です。設定は `.env` で変えられますが、**緩める前に理由を考えてください**。

| 安全装置 | 既定値 | 内容 |
|---|---|---|
| **擬似発注が既定** | `LIVE_TRADING=false` | 明示的に true にしない限り実注文は絶対に出ない |
| **1トレードのリスク** | 資金の 1% | 「いくら買うか」ではなく「いくら失う覚悟か」から数量を決める |
| **1銘柄の上限** | 資金の 20% | 1銘柄への集中を防ぐ |
| **最大保有銘柄数** | 5 | 管理できない数のポジションを持たない |
| **1日の最大通知数** | 3 | バグによる大量発注を物理的に止める |
| **キルスイッチ** | DD 15% | 累計ドローダウンが閾値に達したら全シグナル停止 |
| **承認の有効期限** | 18時間 | 古い承認が突然執行されるのを防ぐ |
| **重複エントリー禁止** | — | 既に保有している銘柄は候補から除外 |
| **署名検証** | — | LINE Webhook の署名を検証。偽の承認リクエストを弾く |
| **userId ホワイトリスト** | — | 登録した本人以外は承認できない |

### ポジションサイジングの考え方

```
1トレードで失ってよい金額 = 運用資金 × RISK_PER_TRADE（既定 1%）
1株あたりの損失幅        = エントリー価格 − 損切り価格
数量 = 失ってよい金額 ÷ 1株あたり損失幅（100株単位に切り下げ）
```

値動きの荒い銘柄は自動的に少なく、穏やかな銘柄は多く持つことになります。
損切り幅が広すぎて 1 単元も買えない銘柄は、自動的に見送られます。

## 7. VPS への本番デプロイ

### 前提
- Ubuntu の VPS（1GB プランで十分）
- ドメイン名（LINE の Webhook は HTTPS 必須。Let's Encrypt で自動取得します）
- DNS の A レコードを VPS の IP に向けておく

### 手順

```bash
# Docker を入れる
curl -fsSL https://get.docker.com | sh

# 取得して設定
git clone <このリポジトリのURL> hinotane && cd hinotane
cp .env.example .env
vi .env                      # API キーなどを埋める
echo "DOMAIN=あなたのドメイン" >> .env

# 起動
docker compose up -d --build

# 初回のデータ取り込み
docker compose exec app hinotane backfill --years 2
```

### LINE 側の設定

LINE Developers コンソールで、Webhook URL に以下を設定して「検証」を押します。

```
https://あなたのドメイン/line/webhook
```

「応答メッセージ」は**オフ**、「Webhook」は**オン**にしてください。

### 動作確認

```bash
docker compose logs -f app          # ログを見る
docker compose exec app hinotane doctor
docker compose exec app hinotane screen --dry-run
```

## 8. 実発注に進むには（Phase 4）

**その前に、必ず以下を満たしてください。**

- [ ] 擬似発注で**最低 3 ヶ月**運用し、成績を記録した
- [ ] `hinotane walkforward` でアウトオブサンプルの期待値がプラスだった
- [ ] 最大ドローダウンの金額を見て、実際に耐えられると判断できた
- [ ] 立花証券 **e支店**（※ストックハウスではない）の口座を開設し、API 利用を申し込んだ
- [ ] `src/hinotane/broker/tachibana.py` を実装した（公式API仕様書を確認してから）

`tachibana.py` は**意図的に未実装のまま置いてあります**。
実発注のリクエスト形式を推測で書くと、誤った銘柄・数量で本物の注文が飛ぶ危険があるためです。
口座開設後に配布される公式仕様書を見てから実装します。
他のコードは `BrokerAdapter` で抽象化済みなので、**このファイルを埋めるだけで済みます**。

実装時のチェックリストは `tachibana.py` の冒頭に書いてあります。

### 立花証券 API の既知の注意点

| 項目 | 内容 |
|---|---|
| セッション | ログインで返る「仮想URL」がトークン。**APIサーバー閉局（03:30）・ログアウト・同一IDの再ログイン**で失効 → 毎朝の自動再ログインが必要 |
| 多重起動 | 同一 ID で二重ログインするとセッションが飛ぶ。プロセスの多重起動を必ず防ぐこと |
| 対象商品 | 国内株式の現物・信用のみ |
| 認証 | 2026/6/27 に v4r8 廃止。以降は API ログイン時の電話認証が不要 |
| 🚨 パスキー | **2026年12月初旬より取引・出金にパスキー認証が必須**。API 発注への影響を口座開設時に必ず確認すること |

## 9. 設定リファレンス

主要な項目のみ。全項目は `.env.example` を参照してください。

| 変数 | 既定値 | 意味 |
|---|---|---|
| `RISK_EQUITY_JPY` | 1000000 | 運用資金（円） |
| `RISK_PER_TRADE` | 0.01 | 1トレードで失ってよい割合 |
| `RISK_MAX_POSITION_PCT` | 0.20 | 1銘柄への投資上限 |
| `RISK_MAX_OPEN_POSITIONS` | 5 | 同時保有の上限 |
| `RISK_MAX_SIGNALS_PER_DAY` | 3 | 1日の最大通知数 |
| `RISK_KILL_SWITCH_DRAWDOWN_PCT` | 0.15 | キルスイッチ作動ライン |
| `RISK_APPROVAL_TTL_HOURS` | 18 | 承認の有効期限 |
| `SCREENER_STRATEGIES` | breakout,pullback,reversal | 使う戦略 |
| `SCREENER_MIN_TURNOVER_JPY` | 100000000 | 20日平均売買代金の下限 |
| `SCREENER_MARKET_CODES` | 0111,0112 | 0111=プライム 0112=スタンダード 0113=グロース |
| `LIVE_TRADING` | false | **true にすると実際に発注されます** |
| `AUTO_EXECUTE_WITHOUT_APPROVAL` | false | true にすると承認を待たずに発注します |

## 10. 困ったとき

### `hinotane doctor` で J-Quants が ❌ になる
`.env` の `JQUANTS_API_KEY`（V2）か `JQUANTS_MAIL_ADDRESS` + `JQUANTS_PASSWORD`（V1）を確認してください。
V2 のダッシュボードで URL が `.../v2` になっている場合は `JQUANTS_BASE_URL` も合わせて変更します。

### 「必須カラムを特定できませんでした」というエラーが出る
J-Quants が返すカラム名が想定と違っています。エラーメッセージに**実際のカラム一覧**が出るので、
それを開発者に伝えてください。`src/hinotane/datasource/jquants.py` の対応表に 1 行足すだけで直ります。

### 候補が 0 件しか出ない
正常な場合もあります（3つの戦略はどれも条件が厳しめです）。確認する順番:
1. `hinotane doctor` で日足の件数を見る
2. `SCREENER_MIN_TURNOVER_JPY` を下げてみる
3. `SCREENER_MARKET_CODES` にグロース（0113）を足してみる

### LINE に届かない
1. `LINE_ALLOWED_USER_IDS` が設定されているか（未設定だと送信されません）
2. LINE Developers で「応答メッセージ」がオフ、「Webhook」がオンか
3. `docker compose logs app` にエラーが出ていないか

### 承認を押しても発注されない
1. 承認の有効期限（既定18時間）が切れていないか
2. 翌営業日の株価データが取得済みか（擬似発注は翌日始値で約定するため）

## コマンドの実行方法

リポジトリ直下で `./hinotane.sh` を付けて実行します。

```bash
./hinotane.sh doctor
./hinotane.sh backfill --years 2
./hinotane.sh screen --dry-run
```

仮想環境の有効化は不要です。ソースの場所を直接指定して起動するため、
pip のインストール登録が壊れていても動きます。

`hinotane doctor` のように直接呼ぶ形（`pip install -e .` に依存）でも動きますが、
コードを更新した直後などに `ModuleNotFoundError` になることがあります。

## 更新

```bash
git pull                    # または GitHub Desktop の Fetch → Pull
bash scripts/update.sh      # 再インストール＋設定診断
```

`.env` は触らないので設定は残ります。
